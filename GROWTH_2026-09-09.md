# Growth work — 2026-09-09

Five changes against the three standing goals: traffic (the priority), trust,
and revenue.

Two things about this round are different from the previous four. The metrics
endpoint was unreachable, so the numbers below come from querying Supabase
directly — which turned out to be an improvement, because it made visible
things the endpoint was not reporting. And the finding it produced is that the
strategy of the last five rounds has been falsified by its own data.

**What has never happened**

Thirteen instrumented events have never fired once, in any environment:
`register_started`, `register_completed`, `launch_subscribed`,

The last three rounds set targets against those counters — "≥ 3

consecutive rounds graded themselves against evidence that did not exist. F19
makes that impossible to do again.

**The archive, measured**

114 articles. Word counts: minimum 573, median 641, maximum **724**. Not one
exceeds 724. One of the 114 cites a source. None contains a table; the only
tags used anywhere in the corpus are `<h2> <p> <strong> <ul> <li> <em>`.

That band is not what UK tax writing looks like. It is the signature of a
single prompt saying "500-700 words" against `max_tokens: 1500`, run 114 times.
The token cap, not the brief, was the binding constraint.

## The conclusion that reorganised the round

Five rounds have built: 15 comparison pages, 3 calculators, a tools hub, 13
topic hubs, site-wide internal linking, an email capture, IndexNow submission,
a subscribable calendar, a status bar, and 114 articles.

The result is 38 page views a week and six search referrals ever.

The 2026-09-08 round named its own falsification condition: *if the archive
grows and search traffic does not move, then the archive is not the constraint.*
The archive has grown by 114 articles over four months. Search traffic is six
visits. The condition is met.

So this round does not build page 131. Three of the five changes are aimed at
the same thing from different directions: **the archive is not an asset that
needs more siblings — it is a liability that needs fixing or pruning.** The
fourth makes the measurement honest enough to tell. The fifth goes after the
one audience that already exists and has never been spoken to.

## What shipped

### F16 — A quality standard the code enforces, not the prompt requests
`lib/article-quality.ts` · `app/api/cron/daily-article/route.ts` · `app/globals.css`

`max_tokens` goes from 1,500 to 8,000, and the brief from "500-700 words" to
1,100–2,600. But the change that matters is that the standard is now checked
rather than asked for. `gradeArticle()` requires:

- 1,100–2,600 words
- ≥ 4 `<h2>`/`<h3>` sections
- at least one `<table>`
- ≥ 3 distinct £ figures — a worked example, not a mention of a threshold
- ≥ 2 citations with a real `gov.uk` or `legislation.gov.uk` URL
- an excerpt ≤ 155 characters

A draft that fails gets one retry with the specific failures handed back
verbatim ("Body is 640 words; it must be at least 1100"). What fails twice is
still stored — the human review gate means nothing reaches the site
unreviewed — but with the report attached so the reviewer knows what they have.

The excerpt limit changed from 45 words to 155 characters for a reason the
audit found: the excerpt is used verbatim as the meta description, Google
truncates that around 155–160 characters, and 45 words is roughly 270. 148 of
155 pages were outside the usable range, losing the last 40% of an
answer-first excerpt — which is the half containing the answer.

`sanitiseArticleHtml()` is also new, and is a security fix rather than
formatting. The body is injected with `dangerouslySetInnerHTML` and the old
pipeline stripped `<a>` and nothing else, leaving `<img src=x onerror=…>` a
working injection into our own pages via a model response. Every tag outside a
15-name allowlist is now unwrapped and **every attribute is dropped**, so there
is no allowlist of "safe" attributes to get wrong later. Verified against
`<script>`, `<iframe>`, `<style>`, `onerror`, `onclick`, `javascript:` hrefs and
a `class` attribute; inner text survives, the tags do not, and the function is
idempotent.

- **Measures:** median word count of articles created after this ships; share
  with ≥ 2 primary sources; `gate.needed_retry` in the cron response.
- **Baseline:** median 641 words, 573–724 range, 1/114 with any source, 0 with
  a table.
- **Target:** every new article ≥ 1,100 words with ≥ 2 gov.uk citations and a
  table — enforced, so the number to watch is the retry rate. If
  `needed_retry` stays at 100%, prompt and standard have drifted.

### F17 — The 113 stubs already published
`supabase/migrations/20260909_article_upgrades.sql` · `app/api/admin/article-review/route.ts`

Fixing new articles does nothing about the 113 that are live, indexed and
uniformly thin. So on alternating days the pipeline rewrites the weakest
existing article instead of writing a new one.

The constraint that shaped the design: an article being rewritten must not go
dark while it waits for review. The rewrite is therefore staged in new
`pending_*` columns beside the live copy, and the published page keeps serving
until a human `promote`s it. The URL never changes — a promoted rewrite is the
same page made better, and its index position and inbound links are the only
thing the archive has that a new page does not.

`weaknessScore()` ranks the queue in code rather than with another model call,
because everything the standard measures is countable. Run against the real
archive: **all 113 published articles fail the standard**, ordered weakest
first — "VAT Recovery on Pre-Registration Expenses" (582 words) leads,
"VAT Flat Rate Scheme" (702 words) is the strongest thing in the queue.

Upgraded articles also gain an internal link. `coversQuery` matched only 3 of
113 titles to the curated query list — the archive predates that list — so the
rest fall back to their own topic hub, which is the only inbound internal link
the older half of the archive gets at all.

**The honest problem with this feature:** one rewrite every other day clears
113 articles in **33 weeks**. That is too slow to matter on its own. `?count=N`
(capped at 10) exists so the queue can be worked in batches, but the real
question is whether to rewrite all 113 or prune the weakest. That is a
destructive, irreversible call and it is yours, not mine — F18 gives you the
data to make it.

- **Measures:** `pending_upgrades` in the review queue; median word count and
  primary-source coverage across the whole archive, over time.
- **Baseline:** 113/113 fail the standard.
- **Target:** ≥ 20 promoted rewrites by 2026-10-09, *or* a decision to prune.

### F18 — What the site actually serves
`app/api/admin/seo-audit/route.ts` · `app/sitemap.ts`

Five rounds have been aimed at search traffic and not one checked the rendered
output. Everything we knew about our own titles, canonicals and structured data
came from reading `generateMetadata` — what we intended, not what shipped.

`GET /api/admin/seo-audit?key=…&all=1` walks the sitemap, fetches every URL
from its own deployment, and reports status, title, meta description, canonical,
JSON-LD types, `<h1>` count, word count and internal-link count, plus grouped
duplicate titles and descriptions. Run against all 157 URLs it found, in its
first execution:

- **`/login` and `/register` were in the sitemap**, serving the homepage's exact
  `<title>` and a canonical of `https://easytax.vip` — telling Google that two
  48-to-71-word auth forms *are* the homepage. Both removed from the sitemap;
  canonical mismatches went 2 → 0.
- **Two articles are published twice**, same title, different dates: "VAT
  Partial Exemption" (2026-07-19 and 2026-09-02) and "Trading Allowance vs
  Actual Expenses" (2026-05-22 and 2026-06-10). Textbook cannibalisation, from
  the old topic-suggestion fallback only checking the last 10 titles.
- 147 of 155 titles exceed 60 characters and are truncated in results; 148 of
  155 meta descriptions fall outside 70–160. F16 fixes the descriptions going
  forward.
- Good news, verified rather than assumed: 155/155 pages return 200, 155/155
  carry JSON-LD, 155/155 have exactly one `<h1>`, none are accidentally
  `noindex`.

One caveat the endpoint reports on itself. Word counts are taken from `<main>`
where a page has one. The first run counted `<body>` and reported the
573-to-724-word articles as 1,211–1,379 words, because shared chrome is worth
~650 words on every page — a measurement that flattered every page equally and
hid the one distinction it existed to draw. `wordScope` is now in every row so
the two can never be silently compared.

- **Measures:** `problem_counts` per run; `duplicate_titles.length`.
- **Baseline:** 2 canonical mismatches, 2 duplicate titles, 147 over-long
  titles, 148 bad descriptions.
- **Target:** canonical mismatches 0 (**done**), duplicate titles 0 by
  2026-10-09, descriptions in range for every article F16 or F17 touches.

### F19 — Metrics that report a zero as a zero
`app/api/admin/daily-metrics/route.ts` · `app/api/cron/daily/route.ts` · `vercel.json`

Three parts.

**`reality_check`.** A block at the top of the funnel listing every
instrumented event that has never fired in production (13), and every one that
has fired only in development (5), computed over all of history rather than the
window. An entry there means the corresponding number below it is not a low
figure — it is nothing at all, and no target set against it has been tested.

**Auth pages are no longer content.** `/login`, `/register`, `/forgot-password`
and `/reset-password` join the non-content prefixes. Nobody arrives at a sign-in
form from a search result. This drops reported 7-day page views from 48 to 38.
The number is supposed to go down.

**One cron path instead of a chain of three.** `growth_snapshots` was empty two
days after the snapshot cron shipped *and was deployed to production* — while
the article cron ran every morning without missing a day. That is the shape of
a per-plan cron limit biting the last entry in a seven-entry file, not a broken
handler. Rather than guess at the plan, `vercel.json` now declares two crons —
under the lowest limit Vercel applies to anything.

The snapshot also no longer travels over HTTP. It used to be
cron → `weekly-review` → `daily-metrics`, two self-fetches to write one row a
day, and a self-fetch is exactly the step that can fail without a trace we can
read: Vercel's deployment protection answers an internal request to the public
hostname with an SSO redirect, so `res.json()` gets a login page and the failure
looks like a metrics outage. `buildMetricsPayload()` is now exported and called
in process. The four date-pinned MTD reminder entries are gone rather than
moved — that handler already refuses to send outside its own window relative to
the real deadline, so calling it daily is both simpler and more correct than
four dates hand-copied into a config file.

- **Measures:** `growth_snapshots.last_7d`; `reality_check.never_fired.length`.
- **Baseline:** 0 snapshots ever; 13 never-fired events; 5 dev-only.
- **Target:** a snapshot row every day from the first run; `never_fired`
  shrinking is the only honest evidence any conversion feature works.

### F20 — The 45 people who already signed up. Built. Not sent.
`lib/reactivation.ts` · `app/api/admin/reactivation/route.ts`

45 accounts, 15 of them HMRC-connected, 0 filings, and not one marketing email
ever sent to any of them. Fifteen people authorised HMRC access — that is not
idle interest — and then nothing happened to them. It is the warmest audience
this product will have for months and it is the single largest gap in the
funnel.

Two segments, because they need different things said:

- `connected_never_filed` — "you connected HMRC and we went quiet; here is your
  next deadline"
- `never_connected` — "MTD started in April, HMRC is auto-enrolling since
  September, here is whether you are in scope"

Both say plainly that HMRC production approval is still pending and that you
cannot yet file through EasyTax, and offer only things that work today. Telling
fifteen people who authorised HMRC access something untrue is how you lose the
only warm audience there is.

**`GET` is a dry run and cannot send.** It returns the segments, masked
recipients, suppression counts and the fully rendered email as the first
recipient would receive it, unsubscribe link included.

**`POST` requires a token of the form `SEND-<segment>-<eligible count>`.** A
boolean is something a script can set; a token containing the exact number of
people currently eligible can only be produced by reading the dry run first, and
stops matching the moment that number changes. Nothing in this repository calls
it. No cron references it. **I did not send this campaign and will not.**

The design fails closed, and that was confirmed for real rather than asserted:
running the dry run against production returned a 503 refusing to build a
recipient list, because `profiles.reminder_opt_out` does not exist — see below.

- **Measures:** dry-run eligible counts; after a send, opens → login →
  hmrc_connections → sa_filings within 14 days.
- **Baseline:** 45 accounts, 0 emails, 0 filings.
- **Target:** for you to set, when you decide to send.

## Two things that need you, not me

**1. The 2026-09-04 migration was never applied to production.**

`profiles.reminder_opt_out` and the `email_sends` table do not exist. The
20260906 migration *was* applied; 20260904 was skipped, five days ago, and no
round noticed because it was written to degrade quietly.

There is no live compliance exposure — `/api/cron/mtd-reminder` correctly
returns 503 and refuses to send without an opt-out column, which is the right
behaviour. But it means **the quarterly reminder cron cannot send at all**. The
7 November deadline puts its next window around 24 October.

Two migrations to run in the Supabase SQL editor, in this order:

```
supabase/migrations/20260904_email_compliance.sql   ← overdue; blocks F20 and reminders
supabase/migrations/20260909_article_upgrades.sql   ← this round; enables F17
```

Both are additive. Until the first runs, F20's dry run returns 503 by design.
Until the second runs, the upgrade pass reports the missing columns and writes a
new article instead.

**2. Rewrite or prune.**

113 thin articles, 33 weeks to rewrite at the default cadence. The alternative
is to `noindex` or delete the weakest of them, which is instant and
irreversible. `/api/admin/seo-audit` and `weaknessScore()` give you the ranking.
I have not deleted anything.
